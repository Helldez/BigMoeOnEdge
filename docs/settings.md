# Settings reference

Every streaming setting: the name every UI shows, the flag it maps to, and what it does. The names,
bounds and help come from one parameter table (`core/src/params.cpp`), which the CLI parses its
flags from and every UI renders its Settings from: one card per group holding the rows a person
usually sets, then **Advanced settings**, one fold holding every other row in the same groups.
Experimental settings are marked here. `bmoe-cli --help` prints the same parameters with their bounds, and
`--describe-params` prints them as JSON.

A default is the CLI's unless the row says otherwise. `bmoe-server`, which both the desktop and the
Android app run, starts from its own: the expert cache at `auto`, overlap on, the chat template on,
a 4096-token context and 1024 tokens to generate.

`--auto` sets them from the machine and the model ([hardware-planning.md](hardware-planning.md)); a
setting passed by hand is left alone.

## Streaming

| Setting | Flag and values | What it does |
|---|---|---|
| Expert cache | `--cache-mb` &nbsp;`auto`, `0` (off), or a size in MiB &nbsp;(default `auto` with streaming on) | Keeps the most-used experts in RAM. `auto` sizes it once at load from free memory; a fixed value is reproducible. Below the engine's floor it only churns. |
| Cache: ceiling | `--cache-ceil-mb` &nbsp;`0` (no cap) or a size in MiB | Caps a cache sized for you: what `auto` may claim at load, and the cache an `--auto` plan picks (the memory it leaves stays free). The OS counts our own mapped weights as free, so uncapped it can ask for more than exists. |
| Cache eviction | `--cache-half-life` &nbsp;`0` (LRU) to `4096` tokens &nbsp;(default `8`) | Which expert the full cache drops: the one least used lately, each use counting half after this many tokens. `0` drops the least recently used, which below one token's worth of experts hits nothing; the default keeps hitting there. Changes no output ([data](cache-sizing.md#the-eviction-policy)). |
| Prompt admitted cold | `--no-cache-prefill-cold` turns it off &nbsp;(on by default) | A prompt of 32 tokens or more prefilled on the CPU puts the experts it reads at the drop end of the cache, so it does not flush what the cache held. Halved what long prompts read on the Mac. Changes no output. |
| Routing recorded for planning | `--routing-record` &nbsp;`0` (off) to `4096` tokens &nbsp;(default `256`) | Keeps which experts the model asked for during its first tokens, so the next `--auto` plan of the same file sizes the cache on the hit rate this model really gets ([how](measured-planning.md#step-1-the-cache-sized-from-the-models-own-routing)). Asks the graph for nothing; changes no output. |
| Routing recorded without streaming | `--record-unstreamed` &nbsp;(off; `--auto` sets it) | Records the routing of a run that does not stream too, at one barrier per MoE layer per token until the record is full. The plan asks for it where a choice waits on that record (the device cache below). Changes no output. |
| Device expert cache | `--device-cache-mb` &nbsp;`0` (off) or a size in MiB | Keeps the experts used most in a device's own memory and computes them there, uploading a miss from the host. Needs the layers on the device and their experts on the host; `--auto` sets all three where the device computes the experts faster than the host ([how](backends.md#experts-computed-on-a-device-from-a-cache-in-its-memory)). Not with `--overlap` or a prefill device. |
| Device cache misses on the CPU | `--device-cache-cpu-share` &nbsp;`0` (off) to `1` | With a device expert cache over resident experts, the share of its misses the CPU computes from the host's copy instead of uploading them, once the cache is full. Below 1 the cache keeps learning which experts are hot. `--auto` arms no share: it is set by hand ([why](hardware-planning.md#who-computes-the-device-caches-misses)). |
| Device cache fill lanes | `--device-cache-fill-lanes` &nbsp;`0` (off) to `8` | EXPERIMENTAL. With a device expert cache in memory the host writes in place (unified memory), reads its misses from the model file straight into the cache on this many lanes instead of copying them from the mapping. `--auto` sets it where it computes a streamed model on such a device ([why](hardware-planning.md#a-streamed-model-on-a-device-that-shares-memory)). |
| Device cache lent to prompts | `--device-cache-lend`, `--no-device-cache-lend` &nbsp;(off) | EXPERIMENTAL. The device expert cache lives in the compute buffer past what the answer's passes use, and a prompt's wide passes take that memory while they run: the cache empties before each and refills from the misses after, so the prompt can be computed in fewer, wider passes without shrinking the cache the answer decodes from. Lossless. Needs a device cache and no misses on the CPU (`--device-cache-cpu-share`). |
| Device cache warmed at load | `--device-cache-warm`, `--no-device-cache-warm` &nbsp;(off; set by `--auto`) | EXPERIMENTAL. At load the device expert cache is filled with the experts this model's own routing record decoded most often, hottest first, up to its slots, so a short session does not pay them as misses on first use. Lossless. Needs the record, which `--auto` reads; the plan warms where the record says the cold misses are first touches and the fill costs no more than they would ([how](hardware-planning.md#a-device-expert-cache-warmed-at-load)). |
| Device cache read-ahead | `--device-cache-read-ahead` &nbsp;`0` (off) to `64` experts | EXPERIMENTAL. The next layer's router, applied to this layer's input, names this many experts per token that are brought into the cache while this layer computes, for every batch the cache serves (a draft's verify batch too), filled ahead where the host writes the cache in place (elsewhere it does nothing: no prediction is built). Lossless; `--auto` sets it to the model's top-k where it fills the cache in place. |
| Read lanes | `--io-threads` &nbsp;`1` to `8` &nbsp;(default `4`) | Reads several expert slices at once. Helps until the flash saturates, which this engine's own measurements put at two lanes on the test device. |
| Direct I/O | `--no-odirect` disables it &nbsp;(on by default) | Bypasses the OS page cache, so the system holds no second copy of what the expert cache already has. Falls back where unsupported. |
| Overlap I/O | `--overlap`, `--no-overlap` &nbsp;(off in the CLI, on in `bmoe-server`) | Issues the next reads while the current layer computes, hiding flash latency behind work. Byte-identical; needs a small optional add-on to llama.cpp ([seam](seam.md)). With layers on a device it keeps a prompt's wide matmuls on the cores, so `--auto` turns the server's default off there unless a device expert cache is armed; `--overlap` keeps it ([why](hardware-planning.md#two-stages-one-composer)). |
| Thread counts to measure | `--trial-threads N[,M]` &nbsp;(empty: none) | Decode thread counts the first answer tries against `--threads`, in alternating windows once the cache has settled; one replaces it only if it decodes 10% faster. Changes no output. The plan sets it when the verdict is kept ([how](measured-planning.md#step-2-lossless-knobs-settled-on-the-first-real-request)). |
| Measure overlap | `--trial-overlap` &nbsp;(off) | Tries the other overlap setting the same way. Needs every layer on the host. |
| Measure the device tier | `--trial-device-cache N` &nbsp;`-1` (off), `0` or `1` | Times this load's decode with (`1`) or without (`0`) a device expert cache, for the next plan to read. Changes no output. The plan serves the side it prices faster and sets this on a load whose side has no measurement on this machine yet; no load is opened to try a side. |
| Batch width | `--ubatch` &nbsp;`0` or a width in tokens &nbsp;(default `0`) | The widest graph a prompt is computed in; its compute buffers are reserved for it, out of the memory the expert cache would get. `0` is as wide as the context up to 8192 tokens, and never narrower than `--image-max-tokens` where a projector is loaded. `--auto` with `0` plans the width: as wide as the context where the memory takes it, narrower where it does not, and at most 8192 where a device computes the graph ([how](hardware-planning.md#the-widest-graph)). Decode is unaffected. |
| Measure the graph width | `--trial-width N` &nbsp;`-1` (off), `0` or `1`, with `--trial-width-narrow N` | Times this load's graph width (`1` the plan's own, `0` the narrower one) for a decision across loads: its decode, the prefill of prompts longer than the narrow width, and the requests it served. Changes no output. The plan serves the width it prices faster and sets both on a load whose width has no measurement on this machine yet. `--trial-width-narrow` alone records the requests and times nothing: the plan sets it where it chose the width before any request was seen. |
| Measure the shared-memory device | `--trial-shared-device N` &nbsp;`-1` (off), `0` or `1` | On a machine whose device reads the host's own memory, times this load's decode of a model held in memory with every layer on the device (`1`) or on the cores (`0`), for the next plan to read. Changes no output. The plan serves the side it prices faster and sets this on a load whose side has no measurement on this machine yet ([how](hardware-planning.md#a-model-held-in-memory-on-a-device-that-shares-it)). |
| Measure the draft | `--trial-spec N` &nbsp;`-1` (off), `0`, `1` or `2` | Times this load's decode, where a verify's reads stay in memory (the model held whole, or a device expert cache that holds a verify), with the model's own MTP head drafting (`1`, with `--mtp`), with a draft model drafting (`2`, with `--drafter`), or without a draft (`0`), for the next plan to read. Changes no output beyond what the draft does. The plan sets it on a load whose side has no measurement on this machine yet, and keeps the fastest draft only where it decodes 10% faster than none ([how](hardware-planning.md#a-model-held-in-memory-drafting-with-its-own-head)). |
| Check the device's answers | `--trial-device-answer NAME` &nbsp;(empty: off) | Before serving, decodes a short fixed sequence on the device this model's layers are on and on the cores, and reopens the model on the cores where the device does not pick the cores' next tokens. `NAME` is the device, the name the verdict is kept under. Needs `--gpu-layers` above 0 and a model held in memory. The plan sets it on a load that moves a whole model onto a device whose answers for it were never compared on this machine ([how](hardware-planning.md#a-model-held-in-memory-on-a-device-that-shares-it)). |
| Keep the faster side of the check | `--trial-answer-mix F` &nbsp;`-1` (off) or more | With `--trial-device-answer`: also times the two sides the check decodes (a token alone, and a graph as wide as a prompt) and serves from the one a request is shorter on, reopening on the cores where they are faster by the trial's margin. `F` is the prompt tokens a request brings per decoded token. The plan sets it where no load has measured both sides on this machine. |
| Tokens per measured window | `--trial-window` &nbsp;`1` to `256` &nbsp;(default `8`) | The length of one timed window of that measurement. For tests. |
| Dense weights | `--dense-weights` &nbsp;`mmap`, `warm`, `anon`, `pinned` &nbsp;(default `anon`) | How the always-needed non-expert weights are held. Decisive far past RAM. `pinned` puts them where the kernel cannot reclaim them at all, on the platforms that have such a store (Android, macOS); `ahwb`, its former name, is still accepted ([data](bench-data/2026-07-21-pinned-dense-ab/findings.md)). |
| Row-stream tables | `--row-stream`, with `--row-stream-mb` &nbsp;(default `64`) | Serves a dense table the graph only gathers rows from, typically the token embedding, out of flash instead of RAM: only the rows about to be read are pulled in, inside a bounded window. Which tables qualify is read off the model's own graph. Lossless ([detail](row-gathered-tables.md)). |
| Unmap the file after load | `--release-mmap` &nbsp;(off by default) | Unmaps the gguf once every weight has been rebound into the engine's own memory, and reopens the read lanes. On Windows a live mapping serialises the streamer's unbuffered reads, so this is worth +46% decode there; on Android it saves CPU instead. Needs `--dense-weights anon` or `pinned`, and the engine declines if any weight still points into the mapping. `--auto` turns it on only where the storage probe saw the slowdown and no card with memory of its own holds layers or the expert cache: a field report crashed inside a graphics driver with it on. Lossless ([data](bench-data/2026-08-29-mmap-serialisation/findings.md)). |
| Temporal prefetch | `--prefetch` &nbsp;`0` (off) to `8` layers | Bets a layer reuses the previous token's experts and fetches them on idle lanes. Needs the cache. |
| Predictive prefetch *(experimental)* | `--predict-prefetch`, with `--predict-spec-max` &nbsp;`0` (retention only) to `8` | Runs the next layer's own router early and fetches what it names. More accurate than the bet above; reading ahead on it still lost its on-device A/B ([why](expert-prediction.md)). |

## Speed and quality

| Setting | Flag and values | What it does |
|---|---|---|
| Drop cold experts | `--drop-cold-experts` &nbsp;`0` (off) to `1.0` | Skips a routed expert only when it is a cache miss *and* the router wanted it less than that share of an even split. Quality is spent only where it buys a read. Lossy and not reproducible: what is skipped depends on what the cache held. |
| Expert substitution *(experimental)* | `--expert-substitute` &nbsp;`0` (off) to `1.0` | Nudges each routing toward experts already in the cache: a resident expert takes a slot only when the router scored it within that margin of the one it displaces. Same number of experts, fewer reads. Lossy and cache-dependent, like dropping ([detail](cache-aware-substitution.md)). |
| Active experts | `--n-expert-used` &nbsp;`0` (the model's own), or any smaller count | Consults fewer experts per token than the model asks for, cutting compute and reads together. Lossy, but reproducible: the same prompt gives the same answer. |
| Speculative drafts | `--mtp`, `--ngram` or `--drafter` with `--drafter-file` (a draft model trained for this one), with `--draft` &nbsp;`1` to `8` &nbsp;and, for a head or a draft model, `--mtp-p-min` &nbsp;`0` to `1.0` | Drafts the next few tokens and verifies the group in one decode, keeping only what the model itself would have produced. Nothing is approximated. Wins when weights move once per group, loses when the wider verify widens each layer's read set ([mtp](mtp.md), [ngram](ngram.md), [drafter](drafter.md)). A draft file goes on the device that computes it fastest (`--drafter-on-devices`, `--mtp-head-on-devices`, `--draft-device NAME`, all set by the plan: [how](hardware-planning.md#where-a-draft-file-is-computed)). |
| Route experts early *(experimental)* | `--route-ahead` &nbsp;`0` (off) to `8` layers | Commits a layer's routing that many layers early, so its reads start early and can never be wasted. Lossy: some slots route differently. Excludes both prefetchers and speculative drafts ([detail](route-ahead.md)). |
| Route-ahead int8 gates *(experimental)* | `--gate-mirror` &nbsp;`auto`, `on`, `off` &nbsp;(default `auto`) | With route-ahead: rank the prediction on an int8 copy of the router gates (a quarter of the bytes) or on their own weights. `auto` times both on this machine at load, or in the `--auto` probe, and keeps the faster ([detail](route-ahead.md)). |

Everything under Streaming changes *how* weights are fetched, never the math, so the answer is the
one the model would have given anyway. The settings in this section are different in kind: they
change *what* the model computes, and they are here because on a device far past its memory the
alternative is often not a slower answer but no answer at all.

They are not interchangeable. Reducing the active experts cuts the routing tail whether or not
those experts were already free to run from memory, and it does so identically every time. Dropping
cold experts spends quality only where it buys back a flash read, which is more surgical but makes
the answer depend on what the cache happened to hold, so the same prompt can come out differently.
Expert substitution is dropping's upstream sibling: instead of deciding whether to pay for a
missing expert it decides whether to need one, and it keeps the routing's width.
Speculative drafts give up nothing at all: it changes how many tokens a pass confirms, not what the
model computes.

Each one is measured rather than assumed, and the numbers live with the method that produced them:
[expert-dropping.md](expert-dropping.md),
[cache-aware-substitution.md](cache-aware-substitution.md), [mtp.md](mtp.md),
[ngram.md](ngram.md), [drafter.md](drafter.md), [route-ahead.md](route-ahead.md). Judge any of
them on your own task before relying on it.
